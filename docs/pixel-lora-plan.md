# Training a 4x pixel-art LoRA (320x180 art grid)

Status: prepared, **not yet trained** (the GPU was busy with other jobs). Everything below was checked on the CPU only. The working files
are in the session scratchpad folder `pilot-lora/` (not in the repo); copy them into `tools/` if the experiment is kept.

## Why

`pixel-art-xl` draws one art pixel per SDXL latent cell, i.e. 8x8 canvas pixels, so a 320x180 art grid would need a 2560x1440 canvas, which
does not fit in 8 GB. A LoRA trained on pixel art enlarged exactly **4x** should draw 4x4 blocks, so 320x180 needs only a **1280x720**
canvas. Post-hoc pixelization of a finished image is rejected: outlines must be drawn with the pixel size in mind.

## Can this machine train it?

Yes, with ComfyUI's native nodes (no pip): `LoadImageTextDataSetFromFolder` -> `MakeTrainingDataset` (VAE + CLIP) -> `TrainLoraNode` ->
`SaveLoRA` + `LossGraphNode`. The node is model-agnostic (it patches every comfy-ops layer of the UNet), so SDXL base works.
Facts from `comfy_extras/nodes_train.py`:

- It trains an adapter on **every** linear/conv layer (biases and norms as small diffs). Alpha is fixed at 1.0, so the LoRA scale is `1/rank`:
  use a high learning rate (1e-3 at rank 16; the node default is 5e-4).
- It deep-copies the model on the CPU, then trains with gradient checkpointing; `offloading` streams weights to the GPU per block.
- Latents of different sizes are trained one at a time (multi-resolution mode), so crops of 512x512 and whole 640x360 images can be mixed.
- The saved file includes the alpha values, so it loads in a normal `LoraLoader`.
- `existing_lora` cannot continue from `pixel-art-xl` (it parses a step count out of the file name).

Memory, **not measured** (the GPU was in use): ~4.4 GB of the 8 GB are held by other programs even when ComfyUI is idle, which leaves
~3.7 GB. SDXL in bf16 is ~5 GB, so `offloading: true` is needed, and rank-16 fp32 adapters plus Adam state add ~1 GB. It should fit at
512x512 crops; whole 960x540 images (tier L) probably do not. Closing browsers or other GPU programs helps. Estimated 2-3 s per pass
(range 1-4), so 750 steps x 2 accumulation = 1500 passes = **about 1 hour** (0.5-2 h). A 12-step smoke test measures the real numbers.

## Dataset (prepared)

True pixel art, enlarged exactly 4x with nearest neighbour, lattice phase 0 at the image origin, every crop origin and size a multiple of 8
px (each latent cell holds exactly 2x2 art pixels), captions starting with the trigger word `px4`. All 57 images pass `lat4.py` (share 1.00,
flat 1.00, 4 px lattice rather than 8).

| Source | Images | Notes |
|---|---|---|
| Six experiment-1 sprites that are **native 4x lattices** (`npc-hooded`, `npc-villager`, `prop-banner`, `prop-barrel`, `prop-crate`, `prop-well`; 256 px art grids) | 36 crops of 512x512 (tier S) + 6 whole (tier L) | On flat magenta, in our own style. Crops overlap by half. The art grid is far denser than props will be in the view. |
| Pilot scenes from `pixel-art-xl` runs B, H, E (decimated x8, enlarged x4) | 14 (tier S) + 1 whole (tier L) | Effectively one house facade; the other pilot runs (D, G, I, J) are near-duplicates and K, A, C are cold or grey, so they are excluded. |
| Concept art | 0 | No pixel lattice (no peak at any period 3-6 px), so it can't be snapped. It stays a style and colour reference. |

The other experiment-1 sprites (`npc-guard`, `prop-chest`, `prop-lamppost`, `prop-stall`, `decal-torch`) and all textures have no lattice.

**Too narrow to train on alone**: one facade, six props, no floors or courtyards. `gen-matrix.json` lists 56 more `pixel-art-xl` generations
(44 scenes at 1920x1080 = 240x135 art px, 12 sprites at 1024x1024; floors, alleys, squares, dungeon corridors, backdrops, props; five rotated
colour palettes), about 50 minutes on the GPU. `bootstrap.mjs` runs them, `step3_bootstrap.py` verifies the lattice, decimates x8, enlarges x4,
crops and captions them into the dataset.

## Risks

- The data is generated by the old LoRA, so the new one may inherit its **greyness, loose layout and odd windows**. Mitigations: pick only
  warm, clean results; rotate palettes; keep the six real sprites in the mix; use captions; don't over-train (stop at ~30 passes per image
  and compare checkpoints by generating).
- Small dataset, overlapping crops: it may overfit to the one facade. More generated scenes are the fix.
- Scale mismatch: the sprites are ~10x denser than props in the view. If small props come out mushy, add generated sprites at 128 px art grids
  and shrink nothing.
- A 4 px grid is not guaranteed to be learned; the validation below decides. If it isn't, retrain with more steps, a higher rank or more data
  before giving up on the route (the fallback is the working 8x route at 160x90 or 240x135).

## Order of work (when the GPU is free)

1. `node bootstrap.mjs`, then `python step3_bootstrap.py` (the dataset grows from 50 to ~190 small images; subsample to ~100 if time is short).
2. `node train.mjs --smoke` (12 steps): check seconds per pass and that it doesn't run out of memory (otherwise `--no-offload` is wrong, rank 8, or close other programs).
3. `node train.mjs` (about an hour), then look at `loss-pixel4x-v1.png`.
4. `node val.mjs pixel4x-v1.safetensors` and `python val_report.py`: 7 generations on a 1280x720 canvas with a lattice-aligned guide, the
   `pixel-art-xl` 8x control, and a floor. Pass means a clean 4 px lattice (`lat4.py --raw`: share >= 2.2/P, flat >= 0.8, odd ratio >= 0.25,
   the same phase everywhere), 1-art-pixel outlines after decimating x4, and a look at the 320x180 result enlarged x2.
